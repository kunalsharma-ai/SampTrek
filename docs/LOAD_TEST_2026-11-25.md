# Load test, 25 November 2026

Measured on main 9990392 plus the fixes in this branch. The test asked how much traffic one SampTrek
server takes, and what breaks first.

## Setup

- One machine with 4 CPUs and 15 GB RAM. It ran the API, MongoDB 8 (replica set) and the load
  generator together, so a real server with its own CPUs does somewhat better than these numbers.
- One API process (`node dist/main.js`, production mode), as in INSTALL.md. One run used two processes.
- Data: 306 projects, 422,000 respondent sessions dated in the last 30 days, and about 120,000
  redirects in the last 24 hours. That is a very busy month.
- The load generator (scratch script, not in the repo) acts like respondents. Each one gets its
  own IP address and respondent ID, and the outcomes are mixed: 40% complete, 45% terminate and 15%
  quota full. The generator runs "closed loop": N respondents at once, each starting the next
  journey as soon as the last one ends.
- Two journeys were tested:
  - **Simple link**: the vendor entry link, then the client's redirect back. That is 2 requests.
    Only the one-open-tab-per-IP check is on.
  - **Full security**: the entry link, the gate page, then the gate submit (gate questions, the
    invisible captcha puzzle, duplicate, TOR, cookie, cross-project, fingerprint, time zone and
    browser language checks), then the redirect back. That is 4 requests.
- Load-test change: the browser puzzle was made easier (8 bits instead of 16) so the load generator
  could solve it. The server checks the puzzle with one hash either way, so the server cost does
  not change.

## Respondent traffic

| Journey | API processes | Respondents at once | Respondents per second | Each step, typical (p95) | Errors |
|---|---|---|---|---|---|
| Simple link | 1 | 10 | 65 | 0.07 s (0.1 s) | 0 |
| Simple link | 1 | 100 | 64 | 0.7 s (1.2 s) | 0 |
| Simple link | 1 | 200 | 55 | 1.4 s (6 s on the redirect back) | 0 |
| Full security | 1 | 10 | 37 | 0.03 to 0.08 s (0.1 s) | 0 |
| Full security | 1 | 100 | 35 | 0.3 to 0.9 s (1.2 s) | 0 |
| Simple link | 2 | 100 | 85 | 0.5 s (1.6 s) | 0 |
| Full security | 2 | 50 | 48 | 0.1 to 0.5 s (0.6 s) | 0 |

- One API process handles about **65 respondents a second on simple links** and about **37 a
  second with full security**. That is about 230,000 and 130,000 respondents an hour.
- The time a respondent spends inside the client survey costs the server nothing. Only entry and
  return do, so thousands of people can be inside surveys at the same time.
- Past about 10 to 25 respondents arriving in the same instant, the server is busy all the time.
  More arrivals then wait in line rather than fail.
- On this machine the CPUs were full: the API used about 2 CPUs and MongoDB about 1.5. With 2 API
  processes the gain was about 30%, limited by the 4 CPUs. On a larger server, or with MongoDB on
  its own server, each extra API process adds close to one process's worth.

### Bug found and fixed: errors on the redirect back

With 50 or more respondents finishing at the same moment in the same market, some redirects back
answered **error 500 and the complete was not recorded**. There were 95 errors in 30 seconds at 50
respondents and 407 at 100.

The cause was that every complete raises the same market and vendor counters inside a MongoDB
transaction. Two transactions that write the same document abort one another, and the 8 quick
retries were not enough.

The fix has two parts:

- The counters are now raised with single conditional updates, the same atomic "only if there is
  room" rule, outside the transaction. These are retried on a conflict.
- The transaction now writes only the respondent's own record. If the outcome is not saved, the
  counts taken for it are given back.

After the fix there were **0 errors** at 10, 100 and 200 respondents at once.

See `recordOutcome` in `src/survey/survey.service.ts` and `retryOnConflict` in
`src/prisma/prisma.service.ts`.

## Staff screens (with the big data set)

The table shows one screen's time with 1, 5 and 10 people opening screens without any pause.

| Screen | 1 person | 5 people | 10 people |
|---|---|---|---|
| Projects list | 0.07 s | 0.16 s | 2.2 s |
| Vendors | 0.5 s | 1.5 s | 5 s |
| Respondents of a 140,000-respondent project | 0.6 s | 1.6 s | 3.8 s |
| Conversion report (30 days) | 0.9 s | 2.3 s | 4.9 s |
| Overall report (30 days) | 1.5 s | 4.2 s | 4.9 s |
| Page of a 140,000-respondent project | 1.8 s | 5.6 s | 12.8 s |
| Dashboard (30 days) | 5.4 s | 11 s | 17 s |

- The server finishes at most about 1.2 heavy screens a second. Real people pause between clicks,
  so about 20 to 25 people can work at the same time, but the dashboard is slow with this much data.
- Dashboards and reports count every respondent in the period each time they open, so their time
  grows with the number of respondents. With 50,000 respondents in a month they should be roughly
  8 times faster. That is an estimate, not measured.
- The slowest part of the dashboard is the redirect check over the last 24 hours. It joins the
  redirect log to the respondents one row at a time: 2.6 s for 120,000 redirects.
- Fixed in this branch: the dashboard asked MongoDB for the same 30-day totals 4 times, once each
  for the totals and the top vendors, projects and clients. It now asks once, which cuts the
  database work for a dashboard by about 3 of those 4 large counts.

## What uses the time

Each simple journey makes about 43 small database queries, and a full-security journey about 79.
Most of them load the same project, market, vendor, client and organisation again for each request.

## Recommendations

1. Merge the fix before heavy fieldwork. Without it, busy markets lose completes with an error page.
2. For more traffic, run 2 to 4 API processes (pm2 cluster) on a server with 8 or more CPUs, or
   move MongoDB to its own server. Plan on about 60 simple or 35 full-security respondents a second
   per API process.
3. Next speed work, if wanted:
   - Cache project settings for a few seconds at entry. This removes most of the repeated queries
     and should give 1.5 to 2 times more respondents per process.
   - Keep daily totals for the dashboard and reports instead of counting every respondent.
   - Store the organisation on each redirect log, so the 24-hour redirect check does not join.
